# 食物优化：下一轮优化方向

2026-09-07 更新。前两项已实现：全部轮次命中共享缓存时直接在主线程汇总，Worker 根据实际计算量扩容。本文保留实施前的诊断依据，最终性能对照与验证见 `docs/food-optimizer-performance.md` 的“共享缓存汇总与自适应 Worker”一节。怪物初始属性模板和跨组合失败复用仍待独立实验；下面的诊断数字不是新改动的加速比。

## 1. 在主线程完成全部轮次已缓存的候选（已完成）

修改前，`src/services/foodOptimizerSearch.js` 在派发前查询每个种子的共享单轮缓存，但无论是否全部命中，都会调用 `client.call()`。Worker 随后检查同一批样本，逐轮汇总，再把结果返回。现在完整命中走 `tryEvaluateFoodOptimizerCachedCandidate`，只有证据不完整或不匹配的候选才派发。

实施前诊断使用全部 28 种食物、两槽、50% 阈值步长、60 秒 × 2 轮、种子 1 和 2。它有 2,785 个逻辑候选、1,174 个可行方案。每种线程数独立运行三次：

| 线程上限 | 实际派发候选数 | 派发前全部轮次已命中 | Worker 进度消息数 |
| -------- | -------------: | -------------------: | ----------------: |
| 2        |        674–675 |              488–490 |       1,970–1,980 |
| 4        |        712–714 |              516–518 |       2,078–2,098 |

四线程约 72% 的派发不需要新的战斗模拟。消除这些往返是确定存在的工作量机会，不能解读成耗时能够减少 72%。这些调用在不同 Worker 上重叠，其累计调用时长也不能直接当作可节省的总耗时。

实现把按轮汇总、累计死亡判断和结果构造提取到 `src/services/foodOptimizerEvaluation.js`，由协调器和 Worker 共用。协调器先确认所有请求轮次的证据均匹配种子、时长、食物、阈值和槽序，再汇总；即使死亡会在前缀超限，也先验证尾轮。任何缺失或失效都回落到 Worker，主线程不运行战斗模拟。

实现与回归保留以下约束：

- 按原种子顺序判断累计死亡；即使后面的轮次有缓存，死亡预算已超限时仍按原前缀结束。
- 缓存命中增加复用轮数，不增加实际模拟轮数；结果仍进入原来的证据记录和排名流程。
- 大量连续命中时定期让出主线程，保留停止响应。目前每 64 次复用让出一次，可沿用同一计数。
- 此分支覆盖有效线程上限大于一的共享缓存，即使自适应调度最终只启动一个 Worker 也可使用；有效上限为一时仍使用 Worker 本地缓存。

部分轮次命中的候选仍由 Worker 处理，每轮结束的进度消息继续转发。连续缓存轮次的消息合并保留为后续实验，需要独立验证取消时的计数。本次只在已判定失败的轮末附加 `rejected` 标记，防止自适应调度把终态误判为仍有后续轮次。

## 2. 根据实际计算量逐步增加 Worker（已完成）

修改前，`src/services/foodOptimizerSearch.js` 按设置上限和逻辑候选数决定线程数。基线结束后，只要不满足“无食物证据覆盖完整目录”的特殊条件，就等待其余 Worker 全部初始化，再开始搜索。现在默认先运行一个 Worker，再由 `src/services/foodOptimizerWorkerPolicy.js` 决定是否扩容；已有 Worker 在扩容期间继续处理任务。

逻辑候选数会被证据压缩，不能直接代表需要并行执行的战斗量。新增诊断中，队伍场景四线程的额外 Worker 初始化中位数为 361.4 ms，全部 Worker 就绪后的搜索中位数只有 184.8 ms。线程启动是该场景值得处理的固定成本。

实施前诊断的完整耗时中位数如下，包含 Worker 启动、基线、搜索和等待退出：

| 场景       | 1 Worker（ms） | 2 Worker（ms） | 4 Worker（ms） |
| ---------- | -------------: | -------------: | -------------: |
| 普通地图   |          710.2 |          661.2 |        1,011.1 |
| 地下城     |        1,629.0 |        1,515.8 |        1,571.9 |
| 全目录两槽 |          879.3 |          971.4 |        1,005.5 |
| 队伍与卷轴 |          693.2 |          950.8 |        1,019.5 |

这些是带诊断计数的有限场景样本，不能与上一轮报告混算改动收益；样本波动明显，也不支持“一律使用单线程”的结论。上一轮无诊断基准同样显示普通地图、跨窗口目录和队伍场景增加线程未必更快，见 `docs/food-optimizer-performance.md`。

策略使用最近 32 条候选调度观测，结合实际耗时、缓存复用、覆盖块的逻辑大小、阶段剩余候选和已测启动成本。普通扩容至少需要两个真实候选的证据；启动时扣除相应工作预算，保留余额。多轮长候选已经完成真实轮次且仍有计算待完成时，可以提前批量扩容，避免等待多个慢候选串行结束。当前已完成真实轮次的候选也参与命中率估计，避免开头缓存命中把后续计算量估为零。基线模拟耗时不参与扩容估计，轮内百分比进度和已知失败的轮末不触发提前扩容。

有效线程上限大于一且开启复用时，从第一个 Worker 起就采用主线程共享单轮缓存，扩容无需迁移。有效上限为一仍用原本地缓存。关闭复用会关闭缓存并使用固定池；`adaptiveWorkers: false` 只关闭扩容策略，保留共享缓存、主线程汇总，以及无食物证据覆盖完整目录时只使用一个 Worker 的特例。32 组合窗口、默认候选优先及尾部任务分担保持原流程；初始化中的 Worker 也纳入取消和失败清理。验收覆盖短任务、长时限地下城、真实三槽全目录和高复用场景，具体结果与限制单独记录于性能文档。

## 3. 请求内复用新怪物的初始属性模板

现有 v2 CPU profile 的离线调用栈归因显示，`Monster.updateCombatDetails` 连同其子调用的采样占比为：普通地图约 13.0%、地下城约 23.6%、全目录约 18.2%。主要路径是新遭遇创建怪物后，经 `reset → clearBuffs` 初始化属性。相关代码在 `src/combatsimulator/zone.js:51`、`src/combatsimulator/combatSimulator.js:895` 和 `src/combatsimulator/monster.js:129`。

可以先统计每次请求中新建怪物次数和唯一初始模板数，再制作隔离实验：按怪物标识、难度及实际房间缩放缓存首次推导的纯数值，只服务于新建、无永久或运行时增益的怪物。相同配置的首次计算仍走原方法。

缓存不能共享当前 HP/MP、Buff 字典、技能对象或冷却状态；仍执行原冷却重置和随机数调用。普通属性重算、方法覆写、控制状态清除及非空增益继续执行原路径。必须通过完整事件轨迹、每次随机数值、最终属性和事件队列顺序对账，不能只比较前十名。采样占比包含必要工作与复制开销，不是预期加速比。

较小的相邻机会是省去食物模式的怪物掉落表构造：`monster.js:106–125` 仍逐项创建 `Drops`，而轻量结果对象的遭遇和掉落统计方法已为空操作。适合独立实验，预期空间小于属性模板；普通战斗仍需要完整掉落表。

## 4. 扩大有证明的失败复用

目前单轮缓存只收完整、未空蓝且未提前结束的样本（`src/services/foodOptimizerRoundCache.js:11`），消耗核心的跨组合复用也有相同条件（`src/services/foodOptimizerInactiveCache.js:79`）。整候选缓存已经能复用同组合的空蓝失败，因此新增方向应聚焦目前没有覆盖的跨组合失败前缀。

最小实现先限定一个已消耗的核心食物、最后一个样本明确空蓝、该种子属于当前请求：目标组合保留同一核心及其阈值证书，额外食物在此前所有检查点都不会触发，即可直接证明候选失败。例如已吃 A 仍空蓝的轨迹，可以覆盖 A+B 中 B 始终不触发的区域；现有无食物证明不能代替已经吃过 A 的轨迹。

现有阈值比较观测、每次食物检查入口及使用后的观测已经提供所需字段，不必先增加引擎逐事件观察。必须读取最后失败样本的 `equivalentThresholds` 和 `inactiveFoodThresholds`，避免拿跨轮聚合下界缩小证明范围。它应作为独立的失败证据，不能伪装为完整单轮样本，也不参与可行方案成本汇总。索引先保持小型、有界，三槽最多查询三个单核心；取得稳定收益后再扩展为整块覆盖。

累计死亡失败依赖前面轮次和剩余死亡预算，不适合直接照搬这一规则。此方向还没有新增命中率或收益实测，优先级低于前两项已量化的调度开销。

## 其他值得保留的方向

- **按实际槽数调整消耗核心缓存优先级。** 当前按固定三槽上限保存一至二食物核心，实际两槽搜索也会保留没有扩展空间的双核心。它们主要充当普通缓存淘汰后的备用证据，可能挤掉更有跨组合用途的单核心；先统计占用与命中，再决定降低优先级。不能未经测量直接删除这类备用证据。
- **过期事件的唯一键索引。** `eventQueue.js:68` 的 `clearMatching` 先复制整堆再逐项删除；现有采样中连同子调用约占 3.3%–6.7%。可先限定原生、唯一的增益过期事件，保留原 `heap.remove(event)` 和通用回调查询的快照语义。索引维护和同时间事件顺序使它比普通查找优化更复杂。攻击事件 `contains` 的已知采样很小，暂不优先。
- **区分战斗输入与展示信息。** `foodOptimizerSnapshot.js:8` 把角色名字纳入签名，但 `playerMapper.js:619` 构造战斗 DTO 时不读取名字。改名会导致报告过期并禁止应用；可以保留报告中的名称快照，同时让计算签名只包含影响结果的字段，减少无意义重跑。
- **独立种子复核。** 当前运行使用固定种子，默认三轮。可以对入选方案和基线用另一组种子配对复核，展示节省的波动及失败轮次。它属于结果可靠性功能，应和原搜索结果分开呈现，不改变完整覆盖的含义。
- **显示实际价格来源。** 当前 ask 缺价按 bid、vendor 回退，整个条目缺失时使用物品商店价，这是共享价格服务的既有规则。食物页展示所选模式和单价，但没有逐项标明实际回退来源；补充来源可避免用户误把所有价格理解为当前卖单。不能把缺整个条目概括为成本为零。

## 实施前诊断范围与复现

诊断脚本：`tmp/audit-food-optimizer-next-directions.mjs`。报告：`tmp/food-optimizer-next-direction-audit/report.json`。

```powershell
node tmp/audit-food-optimizer-next-directions.mjs
```

脚本将当前源码打包到单独目录，保存模块 SHA-256，使用真实 Node Worker，不启动应用或服务。环境为 AMD Ryzen 7 8845H、Node.js v22.20.0；每个场景轮换 1/2/4 Worker 顺序，各运行三次，共 36 次。普通地图和地下城使用 600 秒 × 3 轮、25% 步长；全目录使用 60 秒 × 2 轮、50% 步长；队伍与卷轴使用 1,801 秒 × 2 轮、50% 步长。

四个输入指纹均与上一轮正式基准一致。36 次诊断运行完成状态和候选计数正常，基线、可行总数及前十名逐轮物理结果跨线程一致。这份实施前诊断没有增加逐候选穷举对账；本次实现的独立参考对照、完整候选覆盖及取消测试另外记录于性能文档，不与诊断运行混算。
