# 食物优化：user1 长时普通地图的进一步调查

2026-09-08，针对本次 1,626.4 秒的搜索记录。角色为 `tmp/user1.json`，熊熊星球 T0，24 小时，10% 阈值步长，1 轮，精确前 10。当前源码已经包含装备附近有限优先搜索、按阈值证据选轴、装备属性缓存、空蓝和死亡提前停止、成本下界剪枝。

**本轮没有找到已经验证能让这份输入的完整精确搜索成倍提速的新方案。** 两个看起来能大量减少计算的方向，在长轨迹上都没有得到相应收益。接下来应优先验证增量属性计算；如果目标是尽快拿到可用食物配置，增加时间预算的快速推荐比继续等待全域最优证明更直接。

这里只做离线研究，没有修改生产代码或角色原文件，没有启动项目、浏览器或使用 Playwright。

## 2. 跨组合失败复用：少算很多轮，但未显示全域的大收益

隔离原型按实际消费的一种或两种食物建立索引。核心阈值匹配原轨迹，核心相对槽序保持一致，其他食物在失败前所有检查位置均不触发，才继承失败证明。查询直接匹配阈值区域，避免为每次查询构造完整候选。

原型限于单轮请求，包含空蓝和死亡失败；不是把失败默认阈值推断为整个组合无解，也没有放宽完整单轮成功缓存的准入条件。

### 全部 28 食物的预算试跑

## 3. 共享战斗前缀：必须区分短失败和长轨迹

在当前生产搜索上只观测、不复用前缀。同一随机种子、同一实际槽序下，逐事件比较事件信息、每次食物比较的输入和结果、全部随机数值、玩家及怪物资源值。历史索引不设容量上限，统计不包含快照复制、恢复及查询成本。

| 子域                                 | 候选数 | 实际候选事件 | 与先前轨迹相同的前缀事件 |   比例 |
| ------------------------------------ | -----: | -----------: | -----------------------: | -----: |
| 四食物失败子集                       |  6,095 |    1,109,675 |                  866,496 | 78.09% |
| 当前装备食物的邻近网格，包含可行方案 |     64 |    2,835,800 |                    7,433 |  0.26% |

64 点子域使用原 10% 网格中每种装备食物的三个邻近阈值，并保留食物子集；其可行方案仍需跑满 24 小时。上表分母不含基线、消息和协调器耗时，是可研究的事件工作量，不是实测加速比。

因此不能用失败子集的 78% 推断长时精确搜索可以快四五倍。长轨迹在较早位置就分歧，同组合前缀快照在这个邻域没有足够机会。

另外放宽比较口径，忽略玩家 HP/MP 和食物比较，过滤没有随机数调用的食物恢复 tick 与冷却唤醒，再跨组合比较保留的战斗事件。相似前缀占比也只有 **1.90%**。这一口径不构成安全的状态等价证明，只是额外的轨迹观察；没有据此实现资源回放。

角色的 `mystic_aura` 带有当前 MP 至少 200 的触发条件，其他技能还依赖敌方 HP。食物变化可能改变技能释放、事件顺序和随机数路径，不能直接拿一次完整战斗记录替代所有方案。

## 4. 新热点：增益状态对应的派生属性

对当前装备基线及四个已确认可行候选进行独立 15 秒 CPU 采样。当前版本已启用装备汇总缓存：

- 角色 `Player.updateCombatDetails` 及其子调用约占 **33.9%**。
- 怪物 `Monster.updateCombatDetails` 及其子调用约占 **10.8%**。
- 增益类型索引 `indexBuffsByType` 自身约占 **11.8%**，包含在上述相关调用中，不能重复相加。

另行统计五条完整轨迹的角色重算输入，125,070 次调用只有 227 种有效增益状态。固定角色上下文内，相同增益输入的派生属性输出没有冲突；这不等于省掉 99.8% 的运行时间。

### 为什么整份快照缓存仍不够

隔离原型按有效增益值及其顺序缓存派生属性，每个新模拟角色独占缓存，容量为 512；不缓存当前 HP/MP、事件队列、冷却和随机数状态。命中后仍要生成查询键并复制多项派生属性与基础快照。

最初原型虽然最终榜单一致，但逐属性校验发现基础快照中的 `damageTaken` 没有保留调用前的值。这正是只比较最终榜单会遗漏的内部状态差异。修正后重新进行覆盖和逐事件校验；第一版计时不作为修正后版本的性能结果。

修正后使用同一个 64 候选子域、真实四 Worker 上限，各运行三次，轮换先后顺序；计时不做覆盖展开。

| 实现             | 三次完整耗时（ms）             | 中位数（ms） |
| ---------------- | ------------------------------ | -----------: |
| 当前生产逻辑     | 12,299.0 / 11,127.8 / 11,364.4 |     11,364.4 |
| 派生属性缓存原型 | 10,704.6 / 10,375.2 / 10,352.3 |     10,375.2 |

中位耗时减少 **8.7%**，约 **1.10 倍**速度。全部运行均完成 64 个候选、最终榜单一致。这是小域计时，不能推算原 440 万候选域的收益；也不支持“几乎所有增益状态都重复，所以整体会成倍提速”的判断。查询与快照复制仍有成本，不能把采样热点占比直接换算为可实现的收益。

修正后报告与模块哈希已对齐，汇总见 `tmp/food-optimizer-user1-next/summary.json`。

### 更值得继续验证的精确优化

**改为按变化的增益类型更新受影响的字段，减少整份属性重算和复制。** 例如元素亲和与神秘光环变化的元素增伤字段，不应每次都需要重新遍历装备、重建所有增益索引和计算全部命中、防御、资源上限。

先限定原生、固定角色上下文中的少数直接增伤类型。等级、资源上限、多源交接、装备变化和自定义方法等路径回退完整计算。重新汇总该类型时保留原加法顺序，不能直接用浮点差值累加代替原公式。

这是下一项定向原型的建议，**本轮没有实现或测出其加速比**。33.9% 的角色重算热点即使被完全消除，单独对应的理想上限也只有约 1.51 倍；实际还存在检查和更新成本。不能把它描述成十倍优化。

## 5. 如果目标是大幅缩短等待

建议增加独立的“快速推荐”流程：设置时间或候选预算，从当前装备邻域出发，再扩展单食物替换、多起点与局部阈值搜索；只将完成原 24 小时、原种子轮数验证的方案列入可用榜单。短时运行可以决定访问次序，不能把短时通过当作全天可行，也不能用平均耗蓝外推直接淘汰精确候选。

它能控制寻找可用配置所花的时间，但不能证明原 440 万候选中的全局前 10。保留原精确模式，并允许用户选择继续全域搜索；需要继续的搜索应保留请求快照及覆盖状态，避免重新开始。

当前版本已经允许**停止后应用部分榜单**。`applyFoodOptimizerResult` 要求搜索停止、输入未过期、方案可行且完成全部轮次，不要求整个报告 `complete`。本次已确认的 68 个方案可以用于这一流程；停止后应用的是当前已找到的方案，不能改称全域最优结果。

## 6. 验证与范围

使用 Node.js v22.20.0、AMD Ryzen 7 8845H。真实 Worker 计时包含启动、基线、搜索及退出，排除打包；计时没有与其他基准、CPU 采样或战斗对账并行。前缀统计使用串行适配器，不作为浏览器性能数据。

价格未提供，沿用现有商店价回退；未启用队友、卷轴、社区增益。价格会影响成本界限，全部食物的试跑又使用 50% 网格，因此没有测得用户原 10% 全域输入的最终完成时间和提速比例。

64 候选邻域的前 10 与此前独立完整原生引擎参考一致；新旧覆盖分类一致。派生属性原型另外核对 11 条轨迹，共 610,453 个事件、2,669,274 次随机数调用、125,632 次角色属性重算：事件顺序、随机数、每次属性与基础快照，以及最终消费、死亡、空蓝、停止时刻和阈值证据均一致。核对 106 个生产输入源文件的 SHA-256 及角色文件，研究期间均未改变。

地下城本轮没有另行性能实验。不能将熊熊星球的收益或无收益直接推广到地下城；若将属性增量计算加入共用引擎，需要另行覆盖地下城、队伍和卷轴。
