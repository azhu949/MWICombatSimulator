# 食物优化：增量属性更新与怪物模板验证

2026-09-08，继续研究 `tmp/user1.json`、熊熊星球 T0、24 小时、10% 阈值步长、1 轮、精确前 10。

**本轮找到比整份派生属性缓存更值得实施的方向：增伤 Buff 局部更新。** 配合新怪物初始属性模板，完整子域的耗时减少约 21% 至 31%。其中 1,728 候选的完整搜索从 212.0 秒降到 147.0 秒，约 1.44 倍速度。尚未测得原 4,406,403 候选全域的提速，不能据此外推全部搜索的完成时间，也没有十倍提速的证据。

这些是隔离原型的结果。生产源码和角色原文件没有修改，本轮没有启动项目或浏览器，也没有使用 Playwright。

## 1. 实测结果

均使用真实 Node Worker，四 Worker 上限；计时包含启动、基线、搜索和退出，排除打包。覆盖展开、逐事件核对和 CPU 采样另行运行，没有并行干扰性能计时。

### 当前装备食物的邻近网格

保留桃子软糖、火龙果酸奶、火星莓蛋糕，每种取原网格上最靠近恢复量的三个阈值，同时包含食物子集，共 64 个候选。各版本完整运行三次，轮换先后顺序。

| 实现             | 三次耗时（秒）           | 中位数（秒） | 相对当前耗时减少 |
| ---------------- | ------------------------ | -----------: | ---------------: |
| 当前生产逻辑     | 10.721 / 10.268 / 10.573 |       10.573 |                - |
| 仅增伤局部更新   | 8.084 / 7.808 / 8.011    |        8.011 |            24.2% |
| 仅新怪物属性模板 | 10.348 / 9.766 / 11.474  |       10.348 |             2.1% |
| 两项组合         | 7.434 / 7.860 / 8.781    |        7.860 |            25.7% |

全部完成，前 10 与基线一致。怪物模板单独的收益较小，单次时间也有波动；当前证据支持优先做增伤局部更新，不能把两项的热点占比相加当成提速预测。

### 扩大到原 10% 阈值网格

保留同样三种装备食物，恢复它们的全部原网格阈值，包含食物子集，共 1,728 个候选。两种实现各取得一次完整结果：

| 实现         | 完整耗时（秒） | 实际模拟轮数 | 已确认可行 | 空蓝淘汰 | 死亡淘汰 | 成本剪枝 |
| ------------ | -------------: | -----------: | ---------: | -------: | -------: | -------: |
| 当前生产逻辑 |        211.995 |        1,560 |         57 |      621 |      389 |      661 |
| 两项组合     |        147.028 |        1,560 |         57 |      621 |      389 |      661 |

耗时减少 **30.6%**，速度约 **1.44 倍**。最终前 10 的食物、阈值、价格、消耗、死亡、随机种子轮次结果也逐项一致。这个对比没有通过减少模拟轮数取得收益。

这是单次完整对比，不是三次中位数。脚本原计划重复三次，取得两种实现各一次完整结果后结束后续重复；未完成的重复不计入结果。该子域只含当前三种食物，不是全部 28 种食物的搜索。

### 短失败子域

保留甜甜圈、黑莓甜甜圈、软糖、酸奶，原 10% 网格，共 6,095 个候选。各版本完整运行三次：

| 当前生产逻辑 | 5.960 / 5.580 / 6.018 |        5.960 |
| 两项组合     | 4.824 / 4.698 / 4.661 |        4.698 |

## 2. 首选：只更新变化的增伤字段

`Player.updateCombatDetails` 当前在有效 Buff 变化时，仍会重建装备基础属性，再由 `CombatUnit.updateCombatDetailsFromBuffs` 重算等级、资源上限、命中、伤害、防御、速度等全部派生值。

本角色五条长轨迹共发生 125,070 次角色属性更新，其中 **117,390 次，约 93.9%**，仅涉及水、自然、火增伤。这三个类型在属性推导中各自只写一个直接增伤字段，适合先做局部更新。

隔离原型的实现范围：

1. Buff 源对账和单项到期路径提供变更前后的有效 Buff。
2. 只接受物理、水、自然、火、治疗增幅这五个直接类型，重新按原顺序汇总受影响类型的 `flatBoost`。
3. 使用“装备基础值 + 当前该类型增益总和”写回对应字段，避免用增减差值长期累计浮点误差。
4. 未提供变更信息、涉及其他类型、批量到期、初始化和重置等路径继续完整计算。

原型还保留了 `baseCombatStats.damageTaken` 的原有快照语义。它与上一轮整份缓存中发现的内部状态问题相同：只对比榜单不能验证基础快照正确，逐次属性校验仍然必要。

正式接入时建议先限定食物优化的固定角色请求，并沿用现有原生方法守卫。变更提示应作为内部协议，保留公共 `updateCombatDetails()` 的完整重算语义；装备或基础等级变化、自定义属性方法、无法确认的状态应回退。当前原型没有把这套生产保护全部实现。

## 3. 次选：新怪物的初始属性模板

普通地图反复生成同种同难度怪物。上面的五条长轨迹中，98,080 次怪物属性更新有 96,900 次发生在新实例第一次更新，只有六种怪物初始化上下文。

原型按怪物标识、难度、房间等级及迷宫基础房间等级缓存初始属性，容量 128。仅在新实例第一次更新、没有 Buff、初始受伤增幅为零时尝试复用。后续增益、狂暴和重置等更新回到原有计算。

每次遭遇仍创建新的怪物、技能和掉落对象，保留原先的冷却初始化及其随机数调用，不复用 HP、MP、冷却、Buff、事件或整个怪物实例。正式实现还需要限制到受控的新实例初始化路径，并对原生方法和数据上下文建立守卫。

这项单独的实测收益明显小于增伤局部更新，不建议为了它先引入完整怪物对象池。

## 4. 下一层可以研究什么

组合原型另行进行了约 15 秒长轨迹 CPU 采样。两个原型自身仍是热点：

- `tryIncrementalPlayer` 自身约占 12.0%，其中仍包含基础快照复制、类型判定和 Buff 遍历。
- `restoreFreshMonster` 自身约占 8.9%，其中仍包含键构造及多份属性复制。

因此后续可以验证“减少快路径中的属性搬运”：固定且只读的基础快照能否安全共享；新怪物是否能直接从属性模板完成首次初始化，减少构造默认值之后再次覆盖的成本。需要先检查对象引用、基础快照替换、实例隔离和重置语义，不能共享可变战斗状态。

这是新热点支持的研究方向，**尚未实现或测得额外提速**。上面的采样比例也不等于复制操作各自的成本，更不能直接加到 30.6% 上。两种原型未与上一轮跨组合失败索引或整份派生属性缓存叠加测试。

## 5. 正确性与测量边界

64 点邻域另行展开完整覆盖，四种实现的分类一致，前 10 与此前独立的完整原生引擎参考结果一致。6,095 点失败子域也完成覆盖核对。1,728 点扩大子域核对完成计数、基线、前 10 及分类计数，未另行展开每个被剪枝候选的参考轨迹。

组合原型与当前引擎核对了 23 条轨迹：11 条来自 user1 的基线、失败和可行候选；另 12 条为地下城、队伍与卷轴的合成回归样例。合计比较 **617,138 个事件、2,703,238 次随机数调用、125,943 次角色属性更新、99,772 次怪物属性更新**。事件顺序、每次随机值、资源、技能冷却、Buff、每次属性和基础快照，以及消耗、死亡、空蓝、停止时刻与阈值证据均一致。对象身份兼容性不在这些数值校验之内。

地下城合成样例只用于回归验证，没有测量该角色在地下城的收益，也不覆盖所有队伍光环源交接情况。正式改动共用引擎时仍需补充多源交接、基础上下文变化和自定义方法回退测试。

环境为 Node.js v22.20.0、AMD Ryzen 7 8845H。未提供市场价格，沿用商店价格回退；user1 实测请求未启用队友、卷轴或社区增益。价格会影响成本剪枝，Node Worker 耗时也不是浏览器性能数据。核对了 106 个生产输入源文件、角色原文件及各组构建模块的 SHA-256，均与记录一致。

## 6. 复现材料

研究脚本及原型在忽略目录 `tmp`，汇总为 `tmp/food-optimizer-incremental/summary.json`；报告保留原始耗时、候选输入、来源哈希、覆盖记录及榜单。

```powershell
node tmp/research-food-optimizer-incremental.mjs --domain=equipped-coarse --audit=true --report=coarse-audit.json
node tmp/verify-food-optimizer-incremental.mjs
node tmp/research-food-optimizer-incremental.mjs --domain=equipped-coarse --samples=3 --report=coarse-timings.json
node tmp/research-food-optimizer-incremental.mjs --domain=equipped --variants=current,combined --samples=1 --seconds=300 --report=equipped-timings.json
node tmp/research-food-optimizer-incremental.mjs --domain=failed-small --variants=current,combined --audit=true --report=failed-small-audit.json
node tmp/research-food-optimizer-incremental.mjs --domain=failed-small --variants=current,combined --samples=3 --report=failed-small-timings.json
node tmp/profile-food-optimizer-incremental.mjs
node tmp/summarize-food-optimizer-incremental.mjs
```

以上顺序复现，性能计时不要与其他基准或采样同时执行。较大子域的复现命令有意只运行一次完整对比。生产源码未变，本轮没有重复运行全项目测试或构建。
